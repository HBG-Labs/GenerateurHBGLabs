# P3.3.5 — Procedural Visual Asset Grammar

## Motivation

P3.3A proved that the same deterministic motion vocabulary can express distinct directions, but its reference films exposed an asset-quality ceiling: direction and motion were richer than the visual material being animated. P3.3.5 adds structured, composable visual assets without introducing downloaded media, provider calls, a second renderer, or a P1 change.

The design rule is: **the Director chooses an asset intent; the asset grammar constructs the component tree; the existing deterministic pipeline animates and renders it.**

## Architecture

```text
CreativePlan
  → VisualDirectionPlan
  → bounded AssetIntent
  → ProceduralAssetPlan 0.1.0
  → VisualEntity component tree (VisualPlan 0.3.0)
  → Visual Compiler 0.3.0
  → MotionSpec
  → P1 / RenderPlan
  → existing Remotion renderer
```

Dependencies remain one-way. `procedural-asset-core` depends on data contracts from Visual Core, while P1 knows only ordinary groups, shapes, text, paths and masks. Visual Director Core exposes a deterministic adapter boundary but does not know UI-card internals.

## Implemented contracts

- `ProceduralAssetPlan` schema/version `0.1.0`.
- `ProceduralAssetRequest`: closed family, variant, language, material, density, emphasis, choreography, seed, controlled copy and bounded fixture data.
- `ProceduralComponent`: stable ID, parent, semantic role, hierarchy, region, emphasis, focusability, depth, material surface, geometry and affordances.
- `ProceduralAssetPreflightReport` and `AssetDiversityReport`, both versioned.
- Canonical SHA-256 for every accepted plan and separate registry fingerprints.
- Empty real-migration registry for `0.1.0`; no invented historical migration.

## Component model

An asset is a tree, not an image. A device contains a body, screen group, surfaces, typographic labels, a metric card, chart path, badge/icon and an indicator. Components retain stable IDs during extraction, focus, carry and reassembly. `asset_id` identifies the structural asset; `visual_entity_id` identifies cross-scene persistence and is deliberately separate.

Components expose semantic metadata useful to motion and future QA:

- `emphasis`: primary, secondary, supporting or decorative;
- `focusable` and `group_key`;
- `motion_order` for bounded assembly staggering;
- `depth`: background, midground or foreground;
- allowlisted affordances such as `ASSEMBLE`, `FOCUS`, `EXTRACT`, `EXPAND`, `DRAW`, `CARRY` and `REASSEMBLE`.

P3.3.5 does not introduce a second temporal engine. The Visual Compiler maps component affordances to existing P1 behaviors and timelines.

## Asset families

Fifteen closed/versioned families are registered. Seven have dedicated structured resolvers exercised by semantic goldens: `UI_CARD`, `APP_SCREEN`, `DASHBOARD`, `DATA_CHART`, `GENERIC_SMARTPHONE_FRAME`, `LIGHT_SYSTEM` and `POSTER_FRAME`. The remaining registered families resolve through the generic structured surface system and are marked with their actual limitations in the catalog.

The Product/App reference exercises a device, app surface, dashboard and data chart. Science and Editorial families are covered semantically and through compilation tests; full final films are intentionally not certified in this phase because the existing P1 scene-motion budgets reject their current fixture combinations.

## Materials

Materials are renderer recipes, never shaders or arbitrary CSS. Supported recipes are built from existing P1 shapes, opacity, border tokens and controlled extra layers. `FLAT`, `GRADIENT_LAYERED`, `SOFT_SHADOW`, `BORDERED`, `LUMINOUS` and `MATTE` are supported. `PAPER_LIKE` and `GLASS_LIKE_SIMPLIFIED` remain explicitly simplified.

There is no general blend-mode contract, motion blur, arbitrary filter or raster texture. The term “gradient” describes deterministic layered color fields; it is not a renderer-native continuous gradient.

## Icon system

Eight icons are allowlisted and versioned. Their paths are produced internally from normalized points; no SVG blob, URL or icon pack is accepted. A plan may select an icon ID but cannot inject path data.

## Visual Director integration

P3.3A's `AssetIntent` remains high-level. The P3.3.5 adapter selects a registered family/variant/material/choreography and invokes the deterministic resolver. A presentation adapter can replace controlled fixture copy and remove P3.3A's generic placeholder geometry in asset-led scenes. It cannot emit coordinates, keyframes, CSS or code.

The future provider-facing surface remains compact:

- asset language;
- family and variant IDs;
- density and hierarchy intent;
- material intent;
- registered choreography;
- render-cost/complexity class.

The provider will never control component IDs, component trees, raw paths, SVG, renderer properties or seeds outside declared bounds.

## Limits

Measured defensive limits are:

| Limit | Value |
|---|---:|
| assets per scene | 6 |
| components per asset | 64 |
| nested component depth | 5 |
| paths per asset | 24 |
| particles per asset | 96 |
| charts per asset | 8 |
| UI elements per asset | 48 |
| texture complexity | 32 |
| icon instances per asset | 32 |
| total procedural nodes per scene | 96 |

Critical component limits have exact-limit and limit-plus-one tests. These values protect the existing CPU/DOM renderer rather than advertise capacity.

## Security

Plans are strict data. Unknown fields and IDs are rejected. Preflight rejects cycles, duplicate IDs, excessive depth, non-finite numbers, oversized arrays/strings, raw SVG/HTML/CSS/JS, URLs, filesystem paths, commands and shader data. Runtime source is scanned for provider, benchmark, network, React, Remotion, Chromium, FFmpeg and Blender contamination.

## Determinism and replay

Seeds are mandatory for procedural variation. Same request, registries and seed produce the same component tree and SHA-256. Cross-process tests compare asset, VisualPlan, MotionSpec and RenderPlan hashes. An accepted `ProceduralAssetPlan` can compile to VisualPlan/P1 without Director or provider access.

## Performance policy

Each asset reports layers, paths, masks, text nodes, potential tracks, UI elements, icons and particles plus separate visual-complexity and render-cost classes. Assembly animation is limited to the first six focusable ordered components to prevent a track explosion. Compile work should remain negligible compared with CPU rendering.

## Future boundaries

Not implemented: provider Visual Director, Asset Director, generated or user images, image understanding, subject cutout, photography, true 3D, Blender, audio, Visual Critic, arbitrary morph, general compositor, general path-follow, per-cluster typography, arbitrary materials or shaders. Image slots remain honest unresolved future requirements; they are never replaced silently with a circle or rectangle.

The future escalation policy is procedural first, then approved library/user asset, then generated image, and only then generated video/3D when required. P3.3.5 implements only the first step.
