# P2.5 — First Real AI Provider / Idea → Video

## Objectif et frontière

P2.5 ajoute le premier adapter réel sans déplacer les responsabilités certifiées :

```text
User Idea
  ↓
@motion-engine/provider-openai       ← adapter externe P2.5
  ↓ CreativeProvider P2.4
Creative Gateway                    ← validation non fiable + repair borné
  ↓ PlannerInput
P2.2 Story / Scene Planner
  ↓ CreativePlan + ContentSlots
OpenAI adapter — resolution stage
  ↓ CreativeResolution validée
P2.3 Creative Compiler
  ↓ MotionSpec
P1 Compiler / Render gate
  ↓ RenderPlan
RemotionMotionRenderer
  ↓
MP4
```

L’adapter ne peut produire ni MotionSpec, ni RenderPlan, ni JSX, ni keyframes. Sa sortie traverse les schémas stricts et les validations sémantiques P2.4. P1, P2.1, P2.2 et P2.3 ne dépendent pas du SDK provider.

## Audit et choix provider

Au baseline `5f8b7f86e5e8b74bca9d2146a3645400c4d5eac8`, P2.4 exposait déjà les deux stages, les capabilities, le repair, le timeout, l’annulation, le snapshot et le replay nécessaires. Aucune modification incompatible n’était requise. Le vocabulaire d’échec P2.4 reçoit seulement des catégories additives de transport : authentification, rate limit, réseau, refus de sûreté, sortie incomplète et budget d’appels.

Le premier adapter choisi est OpenAI, avec le SDK officiel `openai@7.23.0` et la Responses API. Ce choix est local à `@motion-engine/provider-openai`; le Gateway Core reste provider-agnostic. Les raisons sont : Structured Outputs JSON Schema natifs, refus inspectables, SDK JavaScript officiel, usage token exposé et propagation standard d’`AbortSignal`.

Le modèle par défaut est `gpt-6-luna`, configurable. La documentation officielle le décrit comme le modèle actuel efficace pour les workloads focalisés/volumiques, multilingue et compatible Structured Outputs :

- [Structured Outputs — OpenAI API](https://developers.openai.com/api/docs/guides/structured-outputs)
- [GPT-6 Luna — OpenAI API](https://developers.openai.com/api/docs/models/gpt-6-luna)

Le modèle est une configuration d’hôte, jamais un choix du Gateway Core.

## Configuration non secrète et secret

Variables d’environnement :

- `OPENAI_API_KEY` : obligatoire uniquement pour le gate réel ;
- `OPENAI_MODEL` : optionnelle, défaut `gpt-6-luna`.

La clé ne peut être fournie que par l’environnement. Elle n’entre pas dans l’objet de configuration, le fingerprint, le snapshot, le manifest, les diagnostics ou les logs. Le fingerprint non secret contient : version adapter, provider, modèle, versions des deux prompts, paramètres de génération, version du schéma et SHA-256 canonique.

Prompts versionnés :

- `creative_planning_prompt@0.1.1` (registre narratif actif et compatibilités de rôles explicites) ;
- `creative_resolution_prompt@0.1.3` (topologie, budgets temporels et contraintes géométriques de sous-titres P1 explicites).

Le SDK reçoit `store: false`, aucun tool et aucune permission filesystem/shell. Le texte utilisateur est sérialisé comme donnée dans une enveloppe distincte des instructions système.

## Structured Outputs et validation

OpenAI exige que tous les champs d’un schéma strict soient requis. Les deux schémas wire rendent donc explicites les absences par `null` (`narrative_archetype`, `scene_id`), puis l’adapter les projette vers les champs optionnels P2.4. Cette adaptation ne relâche aucun contrat :

```text
OpenAI Structured Output
  → schéma wire strict
  → traduction null/optional
  → P2.4 schema validation
  → P2.4 semantic validation
```

Une sortie mockée qui ne respecte pas le schéma wire est quand même renvoyée comme `unknown` à P2.4, qui la rejette et applique son repair borné. La sécurité ne repose donc pas uniquement sur la promesse Structured Outputs.

## Deux stages et qualité éditoriale

Planning reçoit l’idée, la langue, la locale, la durée, le format, l’audience, le ton et les contraintes. Il propose uniquement les champs nécessaires à PlannerInput. P2.2 garde l’autorité sur les beats, scènes et durées.

Resolution reçoit les ContentSlots avec `slot_id`, rôle, canaux, longueur maximale, contexte et exigence factuelle. Il doit distinguer narration et texte écran, conserver `source_required`, décrire les assets sémantiquement et ne fournir aucun `asset_ref`.

Pour un slot `on_screen`, le contexte Stage B contient également `allowed_scene_ids`, les `scene_time_budgets` et le budget générique de la scène admissible la plus restrictive. Ces budgets sont produits avec le profil P2.3 et l’analyse temporelle P1 réelle : le Gateway ne possède aucune seconde formule de vitesse de lecture. La même fonction P1 calcule le nombre de mots, les facteurs de locale/rôle, la lecture minimale et la fenêtre stable après behaviors. Une sortie trop longue reçoit `gateway.output.content_reading_budget_exceeded` et peut être réparée uniquement en raccourcissant le texte. P1 réexécute ensuite obligatoirement `resolveTemporalPlan` et conserve `temporal.impossible_reading` comme erreur bloquante finale.

Le Gateway peut demander au maximum une réparation par stage dans le harness P2.5. L’adapter accepte quatre appels logiques maximum, couvrant planning + resolution et une réparation de chacun. Le SDK est limité à un retry transport par appel. Les retries transport et le repair sémantique restent distincts.

## Frontière registre narratif

L’exposition du domaine narratif est dérivée à chaque génération du `ArchetypeRegistry` réellement sélectionné. Aucune liste parallèle d’archétypes ou de rôles n’est maintenue dans le Gateway ou l’adapter.

Contraintes **EXPOSE_TO_PROVIDER** :

- ID/version et objectifs de sélection de chaque archétype actif ;
- rôles supportés, obligatoires et optionnels ;
- contraintes d’ordre entre rôles ;
- autorisation CTA ;
- durée totale et durée minimale de scène déclarées par le registre ;
- nombre maximal de scènes pré-vérifiable pour la durée de la requête ;
- nombre maximal de contraintes suggérées restant et IDs des contraintes utilisateur déjà réservés.

Contraintes **VALIDATE_LOCALLY** :

- appartenance de l’archétype au registre actif ;
- `require_role` et `forbid_role` limités aux rôles supportés ;
- impossibilité d’interdire un rôle obligatoire ;
- compatibilité CTA et bornes de scènes pré-vérifiables ;
- conflits rôle requis/interdit, narration, assets, min/max scènes, IDs et limites cumulées ;
- validation complète du `PlannerInput`, exécution P2.2 et preflight P2.2 avec le même registre et les mêmes limites.

Une sortie planning n’est marquée acceptée que si cette dernière validation P2.2 réussit. Le JSON Schema Structured Outputs borne les IDs d’archétypes car cette contrainte s’exprime proprement. Les relations cross-field entre l’archétype choisi et ses contraintes de rôles sont transmises dans le contexte structuré et restent vérifiées localement ; elles ne reposent jamais uniquement sur le prompt.

Contraintes **PLANNER_ONLY** :

- sélection finale par objectif lorsque l’archétype est omis ;
- activation et omission des rôles optionnels selon la durée ;
- fusion/split de beats, répétition bornée et nombre effectif de scènes ;
- allocation entière exacte des durées, pacing par rôle et ordre effectif des beats ;
- génération des ContentSlots/AssetIntents et preflight de la structure produite.

En réparation, le diagnostic fournit l’archétype retenu, le rôle incompatible, les rôles supportés/obligatoires/optionnels et les contraintes d’ordre. Le provider doit réparer sa combinaison ; le Gateway ne substitue jamais silencieusement un archétype ou un rôle.

## Frontière de prévalidation finale

Contraintes **PRE-CHECKABLE**, connues avant ou pendant Stage B et utiles au provider :

- schémas, limites de chaînes et champs interdits ;
- appartenance de l’archétype au registre actif ;
- invariants PlannerInput et contraintes croisées P2.2 ;
- topologie `ContentSlot → beat → allowed_scene_ids` ;
- unicité, contenu requis, canaux, langue et exigence factuelle ;
- mappings du profil P2.3 pour visual, motion, typography et transitions ;
- durée de scène, fenêtre stable P1, budget total de mots du calque texte et budget générique le plus restrictif ;
- compatibilité de la résolution proposée avec la lecture temporelle P1, vérifiée sur un MotionSpec provisoire déterministe.
- pour les slots `spoken` réellement sous-titrés, géométrie de sous-titre dérivée du style, du preset, de la safe zone et des polices hashées ; chaque `voice_segment` P2.3 est analysé par le `fitText`/HarfBuzz P1 exact avant acceptation ;
- pour une résolution générique, faisabilité sur toutes les scènes admissibles, avec réparation limitée au raccourcissement du contenu concerné.

Contraintes **COMPILER-ONLY**, qui restent sous l’autorité P2.3/P1 et ne sont pas reproduites dans le Gateway :

- shaping/glyphes définitifs du RenderPlan et toute typographie autre que les unités de sous-titre pré-analysées ;
- layout pixel, safe zones, crop, masks, paths et contraste déterministe ;
- inspection binaire, hash, MIME, dimensions et provenance finale des assets ;
- compilation exacte des behaviors, anchors, tracks, budgets motion et capabilities renderer ;
- EngineLimits complets, RenderPlan, AudioPlan, SubtitlePlan et manifest ;
- validation temporelle finale sur le MotionSpec définitif, dont `temporal.impossible_reading` ;
- rendu Chromium/FFmpeg, intégrité atomique et régression visuelle.

La prévalidation réduit les appels payants inutiles ; elle ne transforme jamais une réussite Gateway en preuve de réussite P1.
P1 conserve donc `text.overflow` comme dernier filet sans seuil relâché. Le contrat ne découpe pas automatiquement une phrase en mots ou phonèmes : une unité affichée simultanément est un `voice_segment`. Plusieurs segments explicitement produits par P2.3 dans une scène reçoivent des plages successives et sont ajustés séparément.

## Erreurs structurées

Les erreurs réelles sont projetées vers le failure model P2.4 :

- secret absent → `provider_auth_missing` ;
- 401/403 → `provider_auth_invalid` ;
- 429 → `provider_rate_limited` ;
- timeout → `provider_timeout` ;
- erreur réseau → `provider_network_error` ;
- refus/content filter → `provider_safety_refusal` ;
- réponse interrompue par la limite de sortie → `provider_output_incomplete` ;
- budget logique épuisé → `provider_call_limit_exceeded`.

Les messages sont fixes et ne recopient pas le corps d’erreur distant. Le SDK officiel gère son unique retry transport et les indications serveur ; aucune boucle de retry maison n’est ajoutée.

## Déterminisme et replay

La génération provider peut varier. Une fois les deux sorties acceptées, `CreativeGatewaySnapshot 0.1.0` fige la frontière créative. Le harness exécute immédiatement un replay et exige l’égalité stricte de :

- PlannerInput ;
- CreativePlan ;
- CreativeResolution ;
- MotionSpec hash ;
- RenderPlan hash.

Le compteur d’appels provider doit rester inchangé pendant le replay. Le MP4 n’est pas rendu une seconde fois.

## Assets et exactitude sémantique

P2.5 ne cherche, ne télécharge et ne génère aucun asset. La preuve utilise la fixture locale CC0 `neutral_landscape` comme fallback abstrait. Chaque mismatch est enregistré dans `editorial-report.json` avec `exact_semantic_match=false`, la description demandée et la politique `abstract_neutral_fixture`. Le rapport ne prétend jamais que cette fixture représente un dinosaure ou une ville moderne.

## Commandes

Quality gate offline, sans clé :

```text
npm run check
```

Gate provider réel explicite :

```text
npm run test:provider:real
```

Commande idée → vidéo :

```text
npm run generate:idea -- --idea "Et si les dinosaures existaient encore aujourd'hui ?"
```

Sans `OPENAI_API_KEY`, ces commandes provider impriment exactement `REAL PROVIDER NOT EXECUTED` et terminent en mode skipped sans créer d’artefact final.

## Sorties réelles

Après succès, la commande finalise atomiquement `out/p2.5/real-provider/`. Une sortie existante n’est jamais remplacée silencieusement. Le dossier contient notamment :

- `p2-5-dinosaurs.mp4` — 1080×1920, 30 FPS, 30 secondes, style Signal explicite ;
- cinq frames ENTER / ACCENT / SETTLE / HOLD / EXIT ;
- `representative.png` et `contact-sheet.png` ;
- request, snapshot accepté, Gateway report et fingerprint provider ;
- PlannerInput, CreativePlan, CreativeResolution ;
- MotionSpec, provenance P2.3 et rapport de compilation ;
- RenderPlan, AudioPlan, SubtitlePlan, dependency graph, preflight et manifest P1 ;
- preuve de replay, métriques, rapport éditorial et hashes d’intégrité.

Le MP4 doit faire l’objet d’une validation humaine explicite. Une compilation réussie ne constitue pas un jugement de qualité artistique.

## Usage, coût et latence

Les tokens input/output/cache et le nombre de requêtes proviennent uniquement du provider. `provider_reported_cost` reste `null` parce que l’API ne retourne pas de coût facturé par requête et qu’aucune grille tarifaire n’est hardcodée.

Les métriques mesurées restent hors hashes : planning provider, resolution provider, validation Gateway combinée, P2.2, construction de résolution, P2.3, phases P1, bundle, render, FPS, frames de contrôle, mémoire Node et total.

## CI

Le workflow Linux standard continue à ne requérir aucun secret. Les tests unitaires de l’adapter utilisent un transport déterministe sans réseau ; l’intégration offline atteint un RenderPlan et vérifie le replay sans rappel provider.

`.github/workflows/creative-provider-real.yml` est un gate manuel distinct. Il exige la confirmation `RUN_REAL_PROVIDER` et le secret GitHub `OPENAI_API_KEY`. Sans secret, il signale `REAL PROVIDER NOT EXECUTED` et ne fabrique aucune preuve. Un succès réel doit publier le dossier d’artefacts P2.5.

## Limites

- aucun appel réel ne peut être certifié sans clé et quota provider ;
- aucune recherche ni vérification factuelle ;
- aucun asset dinosaure exact, génération d’image ou téléchargement ;
- aucune voix, TTS, musique ou SFX réel ;
- timing vocal estimé ;
- transitions P1 éventuellement dégradées en CUT avec diagnostic ;
- contraste sur image potentiellement inconnu ;
- déterminisme garanti seulement après snapshot accepté ;
- déterminisme binaire du MP4 non revendiqué.
