# P3.3A — Visual Director Core

## Scope

P3.3A adds a provider-agnostic direction layer above the certified P3.2 visual vocabulary. It answers _what to choose, when, why, and as part of which sequence_ without emitting pixels, coordinates, keyframes, CSS, JSX, commands, or renderer code.

The implemented flow is:

```text
CreativePlan (canonical P2 content)
  -> VisualDirectorContext
  -> VisualDirectionPlan 0.1.0
  -> Visual Director Gateway / cumulative preflight
  -> deterministic direction resolver
  -> VisualPlan 0.2.0
  -> existing Visual Compiler
  -> MotionSpec
  -> certified P1 compiler
  -> RenderPlan
  -> passive renderer
```

P3.3A contains no provider adapter, network client, prompt, API key, image generation, image understanding, Blender integration, audio generation, Visual Critic, or product UI.

## Dependency graph

The final dependency direction is additive and acyclic:

```text
Creative contracts
  -> Visual Director Core
  -> Visual Core contracts and closed P3.2 registries
  -> Visual Compiler
  -> P1 Core
  -> Renderer
```

P1, P2, P3.1, and P3.2 have no reverse dependency on Visual Director Core. The benchmark corpus and its public-reference provenance remain documentation/data and are not imported by runtime code.

## Implemented contracts

### VisualDirectionPlan 0.1.0

The plan contains only bounded direction decisions:

- canonical source binding: CreativePlan ID/hash and ordered scene IDs;
- active registry fingerprints and DirectorContext hash;
- sequence strategy, motion identity, art-direction intent, motif and lifecycle;
- global pacing, intensity arc, continuity, camera, depth, restraint, and budget;
- one bounded scene decision per canonical scene;
- bounded, adjacent scene bridges;
- controlled asset and material intents.

The plan cannot rewrite narration, facts, scene identity, or scene order. It cannot contain arbitrary URLs, filesystem paths, source code, renderer component names, shell commands, CSS, shader strings, or pixel/keyframe authoring.

### VisualDirectorContext 0.1.0

The context is the authority for immutable facts:

- CreativePlan identity and canonical scene order;
- narrative archetype, canvas and style identity;
- capability support state (`SUPPORTED`, `PARTIAL`, `SIMPLIFIED`, `FUTURE`, `UNSUPPORTED`);
- actual asset/material availability;
- active registry fingerprints;
- defensive limits.

The future provider receives a compact derived planning context, not engine documentation.

### VisualSection decision

P3.3A does not add a separate `VisualSection` entity. The four initial strategies are expressible through ordered scene roles, motif states, global identity/camera/depth policies, and scene bridges. Adding a second grouping topology now would duplicate those authorities. A versioned section layer remains possible when asset-language or identity changes need spans that cannot be represented without repetition.

## Closed registries

### Sequence strategies

Five versioned strategies are registered. Four are exercised by certification fixtures:

- `QUESTION_DISCOVERY_EXPLANATION_REVEAL`;
- `PRODUCT_REVEAL_FEATURES_PAYOFF`;
- `PROBLEM_TENSION_SOLUTION_PROOF`;
- `EDITORIAL_STATEMENT_CONTRAST_PAYOFF`;
- `BUILD_ESCALATE_BREATH_PAYOFF`.

Each entry describes compatible archetypes, structural roles, pacing and intensity defaults, and breath/payoff requirements. Unknown strategy IDs or incompatible archetypes are errors.

### Motion identity recipes

Five versioned recipes are registered:

- `EXPLAINER_CAUSAL`;
- `PRODUCT_POLISHED`;
- `PUNCHY_SOCIAL`;
- `EDITORIAL_PRECISE`;
- `SPATIAL_CONTINUOUS`.

A recipe influences physics, typography intensity, overlap, restraint, depth, camera, phrase and bridge tendencies. It never fixes content, layout, colors, or scene count. A/B tests show that changing only the recipe coherently changes multiple downstream selections without randomness.

### Technique compositions

The registry formalizes the eleven compositions mined in P3.2.5, plus the already-supported causal-explainer composition used by the current engine:

- `TYPE_STATE_TO_TRANSITION`;
- `PRODUCT_FEATURE_TO_VISUAL_METAPHOR`;
- `PERSISTENT_GUIDE_THROUGH_PRODUCT`;
- `UI_DEPTH_CAMERA_FOCUS`;
- `POSTER_DECONSTRUCT_RECOMPOSE`;
- `MIXED_MEDIA_COHERENCE_SYSTEM`;
- `DATA_TO_CHARACTER_STORY`;
- `ABSTRACT_SCIENCE_WORLD_TRANSITION`;
- `BRAND_MOTION_RECIPE_SYSTEM`;
- `TRUE_3D_PRODUCT_REVEAL`;
- `BUILD_COMPLEXITY_BREATH_PAYOFF`;
- `CAUSAL_EXPLAINER`.

Entries declare compatible semantic roles, required capabilities/assets, preferred patterns/phrases, camera/depth expectations, conflicts, alternatives, complexity, relative render cost, and support status. Future or unsupported compositions are rejected. Partial support is preserved as a warning and never presented as full support.

## P3.2.5 integration

P3.2.5 contributes the normalized five-level language model and exact TechniqueComposition definitions. It does not enter runtime as benchmark names, creator names, URLs, or reference-specific logic. The Core consumes normalized generic concepts only.

The four fixtures exercise cross-category language:

| Fixture | Strategy | Identity | Motif | Direction character |
| --- | --- | --- | --- | --- |
| Science | Question → discovery → explanation → reveal | Explainer causal | Light/ray | causal, progressive depth, motivated continuity |
| Product/App | Product reveal → features → payoff | Product polished | Card | persistent UI surface, feature hierarchy, camera follow |
| Problem/Solution | Problem → tension → solution → proof | Punchy social | Grid | dense/open contrast, impact, explicit breath |
| Editorial | Statement → contrast → payoff | Editorial precise | Frame | type-led, generous negative space, mostly static camera |

Blue Sky is fixture data only. The runtime has no subject-specific or archetype-specific branch.

## Resolution and precedence

Resolution is deterministic. The explicit precedence is:

```text
hard engine constraints
  > explicit valid scene direction
  > TechniqueComposition
  > MotionIdentityRecipe
  > SequenceStrategy defaults
```

Significant overrides appear in `VisualDecisionTrace`; incompatible requirements are rejected rather than resolved by object iteration order. Defaults are centralized in the versioned Director registry. The resolver never selects randomly among preferences: the plan makes the creative selection explicitly, while registries provide bounded defaults and compatible expansion.

The trace records only selected IDs, structured reasons and resolved IDs. It does not store model chain-of-thought or unconstrained prose.

## Art direction, motif, camera and depth

`ArtDirectionIntent` separates token choice from composition intent. It controls hierarchy, scale contrast, negative space, density, material intent, and asset-language coherence.

A global motif uses an allowlisted category and the lifecycle `INTRODUCE -> EVOLVE/CARRY -> RESOLVE`. Missing resolution, invalid overuse, and sequence-level repetition are diagnosable. Reuse declared as motif continuity is not treated as accidental repetition.

Camera and depth are sequence policies plus bounded scene intents. Scene-level `STATIC`/`SELECT` overrides are explicit. A camera-continuity bridge is rejected when either side is explicitly static. The resolver remains 2D/2.5D and does not claim true 3D.

## Asset intents

P3.3A describes assets but does not generate them. Active fixtures resolve only controlled `PROCEDURAL_VECTOR` and `UI_SURFACE` intents with currently supported `FLAT`, `GRADIENT`, and `LUMINOUS` materials. Requests for an unavailable product, image, subject cutout, texture, illustration, or 3D object fail instead of silently becoming a circle.

The future boundary is:

```text
AssetIntent -> future ProceduralAssetPlan / approved Asset Director -> validated binding
```

## Visual Director Gateway and preflight

The gateway performs cumulative, dependency-aware checks before VisualPlan compilation:

1. schema and hostile-payload inspection;
2. registry IDs and versions;
3. active capabilities;
4. scene compatibility and canonical topology;
5. global sequence coherence;
6. complexity/restraint budgets;
7. asset/material availability;
8. VisualPlan feasibility.

Independent diagnostics are aggregated. Schema/topology failures block only dependent checks. Every diagnostic carries a code, severity, path, stable target, optional scene/concept, compact context, and suggested action. These targets are suitable for a future bounded targeted-repair protocol.

`SequenceCoherenceReport` is descriptive and contains no artistic score. It reports motif continuity, pacing/layout/bridge variety, focus/intensity progression, camera coherence, and asset coherence.

## Defensive limits and hostile input

The schema and active context bound scene decisions, bridges, patterns, phrases, asset intents, high-complexity scenes, payload bytes and object depth. Exact-limit and limit-plus-one tests cover the important boundaries. Unknown fields, IDs, versions, duplicate IDs, prototype keys, cycles, excessive nesting/size, `NaN`/`Infinity`, malicious strings and impossible references are rejected.

## Determinism, hashes and replay

The Director contract and each registry have independent SHA-256 fingerprints. Accepted outputs carry:

- VisualDirectorContext hash;
- VisualDirectionPlan hash;
- DecisionTrace hash;
- resolved VisualPlan hash;
- MotionSpec hash;
- RenderPlan hash.

Cross-process tests compile the same accepted direction in separate Node processes and compare the complete hash chain. Replay starts from the accepted VisualDirectionPlan and performs zero provider calls.

## Provider attack surface

The future provider may propose only:

- sequence strategy and motion identity IDs;
- art-direction, motif, pacing/intensity, continuity, camera/depth and restraint intents;
- per-scene role, focus, registered composition, layout, pattern/phrase, camera/depth and supported asset intents;
- registered bridge selections and structured motivations.

It may never modify:

- CreativePlan identity, factual/content requirements, scene IDs or order;
- active capabilities, registry contents/fingerprints or engine limits;
- actual asset/material availability;
- renderer values, coordinates, keyframes, CSS/JS/JSX/shaders;
- paths, URLs, commands, provider names, or executable data.

This is the least-authority boundary certified by P3.3A.

## Structured Output feasibility

The candidate contract uses strict objects, closed enums, bounded arrays/strings and explicit versioned IDs. The future adapter will generate the dynamic enum context from active registries, canonical scenes, capabilities, and asset availability. It will not ask a model to guess IDs.

The compact `VisualDirectorPlanningContext` contains only scene summaries, active choices, constraints and immutable hashes. Exact serialized context sizes are reported in certification artifacts; full engine documentation is excluded. Provider-specific schema translation belongs to P3.3B, outside this Core.

## Future snapshot, replay and repair

A future P3.3B snapshot should contain:

- DirectorContext hash;
- normalized accepted generation output;
- accepted VisualDirectionPlan;
- registry fingerprints;
- DecisionTrace and downstream hashes.

Replay is `snapshot -> VisualDirectionPlan -> VisualPlan -> MotionSpec -> RenderPlan` with zero provider calls. Future failures are classified as schema invalid, semantic invalid, unsupported capability, incoherent sequence, repair exhausted, or provider transport failure.

Candidate targeted-repair units are global strategy, scene direction, bridge, motif state, camera intent, TechniqueComposition and asset intent. Canonical CreativePlan facts and registries remain immutable. No repair loop or provider is implemented in P3.3A.

## Security and isolation

Visual Director Core has no React, Remotion, Chromium, FFmpeg, provider, network, benchmark corpus, Blender, or audio dependency. Runtime source contains no dynamic execution, URL fetch, filesystem path, shell, CSS, JSX, shader, or provider-specific model identifier. Renderer and integration code consume only accepted deterministic plans.

## Asset quality ceiling

P3.3A can make sequence decisions safer, more coherent and more varied, but controlled synthetic assets still cap perceived richness. That ceiling belongs to future procedural/premium asset work; it is not hidden or compensated with extra effects here.

## P3.3B boundary

P3.3B may add an external provider adapter around the certified Core:

```text
CreativePlan
  -> compact VisualDirectorPlanningContext
  -> VisualDirectionGenerationOutput
  -> Visual Director Gateway
  -> bounded targeted repair if authorized
  -> accepted VisualDirectionPlan snapshot
  -> deterministic replay pipeline
```

The provider must never write VisualPlan, MotionSpec, RenderPlan or keyframes directly. P3.3A does not select a provider and does not start P3.3B.
