# P2.6 — Final Creative Director / Idea-to-video certification

## Objectif et périmètre

P2.6 certifie le pipeline P2 sans lui ajouter de fonctionnalité. La phase vérifie qu’une idée utilisateur peut franchir les frontières provider non fiable, planification, résolution, compilation créative et compilation P1 sur plusieurs structures narratives. Elle ne certifie ni une qualité artistique premium, ni le déterminisme du provider, ni l’exactitude factuelle d’une réponse IA.

Baseline P2.5 : branche `feature/social-creative-director`, commit `c0171377754a9d82d99d4b973e3e9f7e6ea8f4e9`, run Linux réel `36487283879`.

## Architecture certifiée

```text
User Idea
    ↓
Provider adapter (sortie probabiliste et non fiable)
    ↓
P2.4 Gateway : schéma, sémantique, repair ciblé, snapshot
    ↓
P2.2 Story / Scene Planner
    ↓
CreativePlan
    ↓
CreativeResolution
    ↓
P2.3 Creative Compiler
    ↓
MotionSpec
    ↓
P1 Compiler / preflight
    ↓
RenderPlan
    ↓
Remotion Renderer
```

Le provider ne produit ni MotionSpec, ni RenderPlan, ni JSX, ni coordonnées, ni fichiers locaux. P1 reste l’autorité finale pour le temps, la typographie, les assets, les capabilities, le preflight et le rendu.

## Gates offline

Le quality gate standard, sans secret et sans réseau, exécute :

- tous les tests P1 et P2 ;
- la matrice A–H jusqu’au RenderPlan ;
- un repair combinant dépassement temporel et géométrique ;
- les échecs propres : provider invalide, repair épuisé, asset obligatoire absent, capability absente et scene binding invalide ;
- deux processus Node indépendants produisant le même fingerprint ;
- les goldens P1, P2.2, P2.3, P2.4 et le nouveau golden P2.6 ;
- isolation, contamination et trois smokes renderer réels.

`golden:verify:p2.6` est en lecture seule. Une évolution volontaire exige `golden:update:p2.6`. Aucun ancien golden n’est réécrit par P2.6.

## Gate provider réel

Le workflow manuel `creative-director-certification.yml` exige :

- la confirmation exacte `RUN_P2_6_CERTIFICATION` ;
- une branche/ref explicite et un SHA exact vérifié avant tout appel ;
- Node 24 sur `ubuntu-latest` ;
- le secret GitHub `OPENAI_API_KEY`, jamais écrit dans un artefact ;
- OpenAI avec le modèle explicite `gpt-6-luna` ;
- un maximum de quatre appels par cas et un repair maximum par stage.

La matrice réelle contient quatre cas. Son plafond théorique est donc de seize appels. Trois cas doivent obligatoirement produire un MP4 ; le quatrième fournit une observation supplémentaire jusqu’au RenderPlan et peut se terminer proprement sans invalider à lui seul la certification, tant qu’aucune frontière architecturale n’est violée.

## Targeted repair et échecs

Le repair P2.5 reste inchangé : allowlist de targets, identité et portée de scène immuables, contraintes temporelles et géométriques quantitatives, patch structuré par target, non-targets immuables, merge déterministe puis Full Stage B Preflight. P2.6 n’augmente pas la limite `1/1` et ne relâche aucun seuil.

Un échec avant snapshot ne produit ni CreativeResolution acceptée, ni MotionSpec, ni MP4 trompeur. Une sortie Gateway acceptée qui casse ensuite P2.3/P1 sur une précondition pré-vérifiable est classée comme défaillance architecturale et bloque P2.6.

## Snapshot, replay et déterminisme

La génération provider est probabiliste. Après acceptation :

- le snapshot canonique fige PlannerInput et les sorties structurées ;
- le replay ne reçoit aucune clé et n’instancie aucun provider ;
- PlannerInput, CreativePlan, CreativeResolution, MotionSpec et RenderPlan sont comparés strictement ;
- chaque snapshot réel est rejoué dans deux processus Node distincts ;
- le nombre d’appels provider pendant le replay est strictement nul.

Le déterminisme binaire MP4 n’est pas revendiqué.

## Sécurité

Les tests existants couvrent prototype pollution, payloads excessifs, champs inconnus, réponse hostile, injection JSX/MotionSpec, commandes shell, chemins filesystem, prompt injection, mutation de scope et patches malformés. Le harness P2.6 scanne snapshots, manifests, diagnostics, provenance, métriques, rapports et outputs textuels contre la valeur du secret et des motifs de clé. Les réponses brutes provider restent exclues.

## Performance, usage et observabilité

Chaque cas mesure séparément : planning provider, résolution initiale, repair, validation Gateway, P2.2, construction de résolution, P2.3, phases P1, bundle, rendu, FPS, mémoire Node et total. Les unités input/output/cache et le nombre de requêtes viennent du provider ; le coût reste `null` si le provider ne le retourne pas.

Les performances de runner partagé sont informatives. Seule une régression fonctionnelle ou catastrophique démontrée est bloquante.

## Warnings

- `p1.voice.unused_segment` : non bloquant, candidat à une future phase audio ;
- `creative_compile.transition_degraded_to_cut` : non bloquant, dette technique explicite ;
- `contrast.unknown_on_image` : non bloquant, candidat P3 ; aucun score de contraste n’est inventé.

Les codes réellement observés sont conservés dans `warnings.json` et dans les preflights de chaque cas.

## Human review

La validation humaine reste obligatoire sur les MP4, contact sheets et frames représentatives. Elle vérifie : lisibilité, absence de coupure/overflow, rythme techniquement cohérent, absence d’écran cassé, de scène vide accidentelle et d’artefact renderer évident. Elle ne prétend pas évaluer une direction artistique premium, qui appartient à P3.

## Limites et dette technique

- les assets restent des fixtures abstraites et ne constituent pas une correspondance sémantique exacte ;
- aucune recherche ni vérification factuelle automatique ;
- aucune voix, TTS, musique ou SFX réel ;
- timing vocal estimé ;
- transitions avancées éventuellement dégradées en CUT ;
- contraste sur image potentiellement inconnu ;
- validation humaine visuelle requise ;
- déterminisme garanti uniquement à partir du snapshot accepté ;
- déterminisme binaire MP4 non revendiqué.

P2.6 ne commence ni P3, ni Visual Director, ni Image → Motion, ni génération d’asset.
