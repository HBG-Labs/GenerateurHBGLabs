# P1.4 — Moteur typographique

## Décision

Le moteur de production P1.4 est **harfbuzzjs 1.6.2**, qui embarque HarfBuzz
14.5.0. `fontkit 2.0.4` reste exclusivement une dépendance de benchmark : le
Core ne maintient pas deux chemins de shaping.

Le choix est fondé sur un prototype réel, pas sur la seule facilité
d'intégration. Le rapport machine est conservé dans
`fixtures/p1.4/benchmark/text-engines.json` et peut être régénéré avec
`npm run benchmark:text-engines`.

## Comparaison mesurée

Environnement de la mesure conservée : Node 24.19.0, Windows x64, Noto Sans
Mono variable (`wght=700`, `wdth=85`), 3 000 itérations sur six chaînes.

| Critère | fontkit 2.0.4 | harfbuzzjs 1.6.2 | Décision P1.4 |
|---|---:|---:|---|
| Initialisation | 5,518 ms | 3,475 ms | avantage HarfBuzz sur cette exécution |
| Corpus complet | 1 506,679 ms | 413,662 ms | HarfBuzz ~3,64× plus rapide |
| Glyph IDs / clusters | identiques sur le corpus | identiques sur le corpus | équivalence observée |
| Accents et français | correct | correct | HarfBuzz retenu |
| Kerning / ligatures | GSUB/GPOS intégré | shaping HarfBuzz explicite | résultats identiques sur la fixture Playfair |
| Font variable | `getVariation`, axes exposés | axes exposés et variations appliquées | HarfBuzz validé sur `wght` et `wdth` |
| Précision | avances flottantes | positions en unités de font converties en px | HarfBuzz fournit directement clusters et positions |
| Déterminisme | déterministe avec version/font/options figées | déterministe avec version/font/options figées | versions, hash et axes inscrits au plan |
| Licence | MIT | MIT | compatibles avec le projet |
| Node 24 | prototype réussi | prototype réussi | les deux compatibles |
| Intégration | API haut niveau riche | API de shaping plus basse, WASM | coût accepté pour garder le shaper explicite |

Les écarts de largeur observés sur Noto Sans Mono sont des fractions liées à
l'arrondi des avances. La preuve OpenType ne prétend pas qu'une substitution
de ligature existe dans chaque police : elle vérifie les glyphes, clusters,
positions et largeurs produits par les deux moteurs sur une police distincte.

Sources amont : [HarfBuzzJS](https://github.com/harfbuzz/harfbuzzjs),
[fontkit](https://github.com/foliojs/fontkit).

## Contrat de production

Le compilateur reçoit les octets des polices ; il n'effectue aucun accès
disque et aucun fallback système. Une ressource absente, un hash différent,
un axe hors plage, une signature SFNT invalide, une table hors limites ou un
glyph manquant produit une erreur structurée.

Le `RenderPlan` conserve pour chaque run :

- `source_text` et `formatted_text` ;
- largeur mesurée, taille, tracking, poids et axes ;
- ascent, descent, line gap et baseline de chaque ligne ;
- glyph ID, cluster, position, avances et offsets.

La configuration de shaping et les versions `harfbuzzjs`/HarfBuzz sont aussi
inscrites dans la provenance du plan et du manifeste.

## Français et fitting

`TypographyFormatter` intervient après l'intention éditoriale. Il conserve le
texte source et applique seulement des transformations typographiques
traçables : apostrophe courbe, espaces insécables, espaces fines insécables
avant `?`, `!` et `;`, espace insécable avant `:`, guillemets français et
unités simples.

Le wrapping ne coupe jamais une NBSP/NNBSP. Le fitting essaie dans cet ordre :
taille préférée, wrapping autorisé, line-height resserré, réduction par paliers
jusqu'à la taille lisible minimale, puis erreur `text.overflow`. Aucun texte
n'est réduit au-dessous du minimum configuré et Chromium ne décide jamais du
layout après compilation.
