# P2.2 — Deterministic Story / Scene Planner

## Objectif et frontière

P2.2 transforme un `PlannerInput 0.1.0` validé en un `CreativePlan 0.1.0` validé par P2.1. Il s'arrête avant MotionSpec.

```text
PlannerInput
    ↓
Planner validation
    ↓
Archetype Registry
    ↓
Story beats + Story arc + Content slots
    ↓
Scene merge / split + integer duration allocation
    ↓
PlanningPreflight
    ↓
CreativePlan 0.1.0
    ↓
P2.1 validation + CreativePreflight
```

Le planner ne produit ni MotionSpec, ni primitive motion, ni coordonnée, ni frame, ni keyframe, ni code renderer. Il ne rend aucune vidéo et ne dépend d'aucun provider ou réseau.

## PlannerInput 0.1.0

Le contrat strict contient :

- un ID stable et une version ;
- le sujet, le creative goal et la réaction souhaitée ;
- l'audience et son niveau de connaissance ;
- la langue et la locale ;
- la durée cible en millisecondes entières ;
- le format générique `vertical_short`, `square` ou `landscape` ;
- le ton, le pacing et la densité `minimal | low | medium | high` ;
- un archétype optionnel ;
- le mode factuel `factual | creative | mixed` ;
- la préférence CTA `none | soft | explicit` ;
- des contraintes structurées ;
- du contenu fourni, identifié, canalisé vers `spoken` et/ou `on_screen`.

La durée est exprimée en millisecondes et non en frames. Le planner ne traduit jamais le contenu fourni.

## Registre d'archétypes

`ArchetypeRegistry` accepte des définitions externes validées. L'ajout d'un archétype ne nécessite pas de modifier le Planner Core. Chaque définition contient :

- ID et version ;
- goals de sélection et priorité ;
- rôles supportés, requis et optionnels ;
- contraintes d'ordre ;
- règles de beats ;
- stratégie de durée et bandes de nombre de scènes ;
- stratégie de pacing ;
- règles de validation.

Le registre par défaut fournit :

| Archétype | Structure principale |
|---|---|
| `HYPOTHETICAL` | hook, premise, consequence, escalation, reveal, payoff |
| `EXPLAINER` | hook, context, explanation, example, takeaway |
| `PROBLEM_SOLUTION` | hook, problem, consequence, solution, demonstration, payoff |
| `LIST` | hook, item, development, strongest_item, takeaway |
| `COMPARISON` | hook, comparison_a, comparison_b, contrast, takeaway |
| `REVEAL` | hook, setup, tension, partial_information, reveal, payoff |
| `DEMONSTRATION` | problem, context, action, result, proof, takeaway |

Tous les rôles optionnels ont un seuil d'activation temporel propre à la définition. Les rôles obligatoires ne sont jamais supprimés silencieusement.

### Sélection

1. Un `narrative_archetype` fourni est utilisé exactement.
2. Sinon, le registre recherche un `selection_goal` correspondant au creative goal.
3. Sans correspondance, `EXPLAINER` est le fallback déterministe et cette décision est rapportée.

Le topic brut n'est jamais analysé pour simuler une compréhension sémantique.

## Story beats et arc

Chaque beat possède :

- un ID dérivé du PlannerInput, de l'archétype, de sa version, du rôle et de sa position ;
- un rôle narratif ;
- un but sémantique non rendu ;
- une importance entière ;
- un poids de durée entier ;
- une densité qualitative ;
- ses voisins ;
- ses statuts required et splittable.

L'arc est une séquence explicable de phases `curiosity`, `context`, `tension`, `escalation`, `reveal`, `resolution`, avec direction `rise`, `hold` ou `fall`. Ce n'est ni un score d'attention, ni une prédiction de rétention.

## Content slots

Les slots préparent une future génération ou recherche sans en effectuer aucune. Rôles disponibles :

- `hook_text` ;
- `narration` ;
- `explanation` ;
- `factual_claim` ;
- `reveal` ;
- `cta` ;
- `statistic` ;
- `comparison` ;
- `label`.

Chaque slot contient ID, beat, rôle, langue, obligation, contexte sémantique, longueur maximale, canaux et exigence factuelle.

- `resolved` signifie que le texte provient exactement de `provided_content` ou de `cta.text`.
- `unresolved` signifie qu'une phase future doit fournir, générer, rechercher ou vérifier ce contenu.

Un slot unresolved n'est jamais copié dans le CreativePlan comme faux texte. Le CreativePlan conserve uniquement le sens de scène et les intentions. Un slot obligatoire unresolved produit un warning stable, non un texte inventé.

Pour `factual`, les slots explicatifs/factuels demandent une source. Pour `mixed`, ils recommandent une source. Un `source_slot` reste un emplacement de provenance, jamais une source inventée.

## Allocation de durée

Tous les calculs sont effectués en millisecondes entières.

1. L'archétype sélectionne ses beats obligatoires et les beats optionnels activables pour la durée.
2. Sa bande temporelle fournit un nombre de scènes cible.
3. Le pacing ajuste ce nombre de façon bornée : slow réduit, fast/aggressive augmentent.
4. La durée et `minimum_scene_ms` bornent le maximum réellement possible.
5. Si les beats sont plus nombreux que les scènes, des groupes contigus sont fusionnés.
6. Si les scènes sont plus nombreuses que les beats, les beats splittables les plus importants sont répétés de façon déterministe.
7. Chaque scène reçoit son minimum, puis le reste est distribué par poids avec méthode du plus fort reste et tie-break sur ID.

Invariant :

```text
sum(scene.duration_ms) === PlannerInput.target_duration_ms
```

Aucun arrondi flottant cumulatif n'intervient. La projection P2.1 utilise ensuite `duration_ms / 1000` pour les durées sémantiques.

Les durées 5, 10, 15, 30, 45 et 60 secondes sont testées. À 5 secondes, les beats obligatoires de l'archétype hypothétique sont conservés mais fusionnés en deux scènes. À 60 secondes, les beats importants peuvent être splittés.

## Planification des intentions

`DEFAULT_PLANNING_POLICY` contient des mappings sémantiques configurables par rôle. Ils ne décrivent aucune esthétique de marque.

Exemples :

- hook → text dominant, headline bold, motion punchy, cue impact ;
- explanation → diagram, motion precise, typographie technical ;
- comparison → comparison ;
- reveal → image dominant, motion dramatic, transition reveal ;
- takeaway/payoff → text dominant, motion restrained.

Une autre politique peut être injectée sans changer le planner.

### Audio et sous-titres

Le planner produit uniquement : narration required/optional/none, musique souhaitée, ambience, silence et cues sémantiques `impact`, `whoosh`, `rise`, `hit`, `transition`, `reveal`. Aucun fichier, TTS, waveform ou timing mot à mot n'est créé.

Lorsque la narration est autorisée, les sous-titres sont demandés au niveau global. Une scène ne demande localement des sous-titres que lorsqu'elle contient réellement du contenu parlé résolu.

### Assets

Les besoins sont `image`, `illustration`, `icon`, `background`, `diagram` ou `none`. P2.1 ne possède pas encore un kind `diagram` distinct : le planner le projette sans perte opérationnelle vers `illustration` avec la contrainte `diagrammatic`, tandis que le PlanningReport conserve `diagram`.

La description d'asset est une query sémantique composée du topic, du rôle et du but. Elle ne contient ni URL, ni chemin, ni prompt propre à un provider.

### CTA

- `none` n'ajoute aucun CTA ;
- `soft` l'ajoute uniquement lorsque le budget le permet ;
- `explicit` exige le rôle CTA ;
- un texte absent reste un content slot unresolved.

Le planner n'ajoute jamais automatiquement une phrase d'abonnement.

## PlanningPreflight

La frontière publique `runPlanningPreflight()` vérifie :

- budget temporel exact ;
- durée minimale des scènes ;
- références beats/scènes/slots ;
- conservation des rôles obligatoires ;
- ordre de l'archétype ;
- IDs de sortie dupliqués ;
- limites beats, scènes, slots et assets.

L'orchestrateur ne peut annoncer un succès lorsque PlanningPreflight ou CreativePreflight contient une erreur.

## PlanningReport 0.1.0

Le rapport structuré contient :

- hash canonique du PlannerInput ;
- fingerprint du registre ;
- archétype, version et mode de sélection ;
- beats et arc ;
- scènes, fusions, splits et durées ;
- slots resolved/unresolved ;
- assets ;
- décisions structurées ;
- diagnostics ;
- hash et statut preflight du CreativePlan.

Les diagnostics reprennent le modèle P2.1 : code, severity, path, node/scene, contexte et action suggérée.

## Limites défensives

| Limite | Valeur |
|---|---:|
| PlannerInput JSON | 256 KiB |
| Profondeur | 16 |
| Nœuds | 10 000 |
| Chaîne individuelle | 20 000 caractères |
| Durée | 3 000–180 000 ms |
| Contraintes | 64 |
| Contenus fournis | 64 |
| Volume de contenus fournis | 30 000 caractères |
| Beats | 24 |
| Scènes | 24 |
| Content slots | 128 |
| Asset intents | 64 |

L'inspection défensive intervient avant Zod. Elle refuse prototype pollution, objets non JSON, cycles, profondeur/volume excessifs et nombres non finis. Les propriétés inconnues sont refusées.

## Fixtures et goldens

- Hypothetical 30 s : Terre, fr/fr-FR, progression complète et slots unresolved ;
- Explainer 30 s : contenu éducatif résolu et exigence de source ;
- Product demo 20 s : produit générique ;
- Minimal 5 s : fusion narrative ;
- Long 60 s : scene splitting ;
- Invalid : contradictions multiples.

Le golden sémantique compare l'entrée canonique, les beats, les scènes, les durées, les content slots, le hash CreativePlan et le PlanningReport. La commande normale ne peut que vérifier :

```text
npm run golden:verify:p2.2
```

Une mise à jour exige l'action explicite :

```text
npm run golden:update:p2.2
```

## Déterminisme et isolation

À PlannerInput et registre identiques correspondent exactement les mêmes beats, scènes, allocations, IDs, intents, CreativePlan, rapports et hashes. Cette propriété est testée dans deux processus Node séparés.

Le test d'isolation copie le Creative Core seul et exécute son typecheck et tous ses tests sans Motion Core, renderer, React, Remotion, navigateur, application, provider ou réseau.

## Hors périmètre

- aucune invention intelligente de hook ;
- aucune recherche ou vérification factuelle ;
- aucune génération de texte, image, voix, SFX ou musique ;
- aucune conversion CreativePlan → MotionSpec ;
- aucun rendu ;
- aucun score viral, de rétention, d'engagement ou d'attention ;
- aucune logique spécifique à une plateforme ou une marque.
