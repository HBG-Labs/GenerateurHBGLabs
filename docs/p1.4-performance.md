# P1.4 — Performance et mutualisation Remotion

## Mesure indicative avant référence

Mesure Windows x64, Node 24.19.0, Chrome local, 210 frames par vidéo. Les
valeurs de rendu dépendent de la charge machine ; les métriques brutes de
chaque run sont dans `out/p1.4/metrics.json`.

| Mesure | P1.3 enregistrée | P1.4 mesurée | Lecture |
|---|---:|---:|---|
| Compile deux styles | 89,68 ms | 77,75 ms | échantillon unique, caches chauds : pas de conclusion de vitesse |
| Render Signal | 24,62 s | 30,16 s | Image/Mask/Path et traitements visuels ajoutent du travail |
| Render Nocturne | 24,95 s | 26,39 s | hausse contenue sur cette exécution |
| Max RSS Node hôte | 791,0 MB | 862,7 MB | +9,1 %, sans agréger Chromium/FFmpeg |
| Bundles pour deux vidéos | 8,65 s + 7,47 s | 14,94 s + 0 s | second rendu réutilise le bundle |

Le shaping a son benchmark dédié : 3 000 itérations sur six chaînes donnent
413,662 ms avec HarfBuzzJS contre 1 506,679 ms avec fontkit sur la machine de
référence. Le coût Image/Mask/Path est mesuré ensemble dans la verticale P1.4,
car c'est leur composition réelle qui importe ; aucun micro-benchmark
artificiel n'est présenté comme temps de rendu utilisateur.

## Mutualisation

`RemotionMotionRenderer` construit le bundle une fois par instance, mémorise
la promesse pendant une construction concurrente, puis réutilise le même
`serveUrl` pour vidéos et stills. Chaque requête conserve ses propres
`inputProps`, ressources vérifiées et `RenderPlan`. `dispose()` supprime
uniquement le dossier temporaire résolu sous le répertoire temporaire système.

La seconde vidéo doit rapporter `bundle_reused=true` et `bundle_ms=0`. Cette
mutualisation ne partage ni décisions créatives ni état de frame ; elle ne
change donc pas les hashes de plan ou le déterminisme.
